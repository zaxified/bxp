# CLAUDE.md — examples

Guidance for Claude Code when authoring or editing the `examples/` tree.
For monorepo-level context see [`../CLAUDE.md`](../CLAUDE.md).

## Purpose

`examples/` is **documentation and teaching material**, not a regression gate.
Each example is a self-contained, runnable demonstration of one data problem
the bxp engine solves — config + input + expected output + a narrative readme.
It is the place a new user (or a prospective evaluator) goes to see "what is
this tool actually for, on real data".

Regression coverage lives in [`../datasets/`](../datasets/) (gated by
`scripts/test-02-datasets.sh`). `examples/` is **not** in any `test-NN-*.sh`
phase — its `.expected` files are hand-verified goldens, exercised manually and
by `scripts/bench/verify-output.sh` (which runs `bxp-cli` over every
`real-world/` subdir for output capture), not by `scripts/test.sh`.

## Two kinds of example

- **Real-world use cases** (`real-world/`) — a real, publicly available dataset
  with a **cited source** documenting a genuine, reproducible data problem. The
  committed `sample.csv`/`sample.json` is a small **real slice** of the upstream
  file; a `fetch-full.sh` (where present) pulls the complete file for a scale
  run. Never synthesise real-world data — if a problem can't be backed by a real
  sourced dataset, it belongs in the roadmap, not here (see
  [[feedback_real_world_problem_first]]).
- **Teaching examples** (`basic/` → `intermediate/` → `advanced/`) — small,
  synthetic, hand-constructed inputs that isolate one engine feature at a time.
  The data is fabricated **on purpose** and the readme says so explicitly
  ("Synthetic / teaching example."). The *problem class* must still be real and
  universal; only the rows are invented.

## Tiers

| Dir             | Tier         | Content                                                            |
| --------------- | ------------ | ----------------------------------------------------------------- |
| `real-world/`   | —            | Real sourced datasets, one documented problem each                |
| `basic/`        | teaching     | One feature, minimal input                                        |
| `intermediate/` | teaching     | A few features combined                                           |
| `advanced/`     | teaching     | Multi-pass pipelines, combine/join patterns, capstones            |

## Per-example directory layout

Every example dir holds the same fixed file set:

```text
<tier>/<example-name>/
  00-readme.md     ← the narrative (see section structure below)
  sample.json      ← the bxp-cli config (template(s) live here)
  sample.csv       ← input (or sample.json input for JSON-input examples)
  sample.csvx      ← committed engine output
  sample.expected  ← hand-verified golden — byte-identical to sample.csvx
  fetch-full.sh    ← (real-world only, optional) pull the full upstream file
```

- The config is always named `sample.json`; the run command is
  `bxp-cli --config ./sample.json --template <id>`.
- `sample.expected` is the **final-only** golden and must match `sample.csvx`
  1:1. Regenerate output by running the example, then verify the diff by eye
  before updating `.expected`.
- JSON-input examples carry the input as `sample.json`-shaped data per the
  example's own convention; check the readme's "Run it." block for the exact
  invocation.

## Readme section structure (`00-readme.md`)

The index generator parses these by heading/bold-lead, so keep them verbatim:

- `# Title` — h1, becomes the index entry title.
- `[← all examples](../../README.md)` — back-link.
- `**What.**` — one-paragraph statement of the transformation.
- (teaching only) `**Synthetic / teaching example.**` — the fabricated-data
  disclaimer.
- `**Why interesting.**` — why the problem class matters (the index pulls the
  first line of this).
- (real-world) `**Problem class documented in.**` / source citations — the
  upstream dataset and a reference proving the problem is real.
- `**The trick.**` — the key expression(s), with prose explaining them.
- `**Run it.**` — the exact `bxp-cli` command in a fenced block.
- `**Smoking gun.**` — the before/after that proves the point.

## The index (`README.md`) is generated

`examples/README.md` is a **signpost** auto-generated by `examples/autoindex.sh`
from each readme's `# Title` + `**What.**` / `**Why interesting.**` lines.

- **Do not hand-edit `README.md`.** Run `bash examples/autoindex.sh` after
  adding, renaming, or re-describing an example.
- The index is a pure signpost (one-line What/Why per example + a link); it
  deliberately carries no run commands or data — those live only in the
  per-example readme.

See [[reference_examples_conventions]] for the longer-form rationale.

## Adding an example

1. Pick the tier. Real problem with a sourced dataset → `real-world/`;
   feature-isolation drill → the teaching tier matching its complexity.
2. Create `<tier>/<name>/` with the file set above.
3. Write `sample.json` (the config) and the input; run `bxp-cli` to produce
   `sample.csvx`; eyeball it; copy to `sample.expected`.
4. Write `00-readme.md` following the section structure.
5. Run `bash examples/autoindex.sh` to refresh the index.

## Conventions

- All readmes and comments in English.
- Real-world data must be **real and cited**; teaching data must be **labelled
  synthetic**. Never blur the two.
- Rank candidate examples by **user value**, not implementation ease — an easy
  example demonstrating the wrong thing is worth less than a harder one that
  shows a real pain point ([[feedback_classify_by_value_not_difficulty]]).
